# internet-engineering-git

سؤال اول: تفاوت git merge و git rebase

هر دو دستور "git merge" و "git rebase" برای ترکیب تغییرات شاخه‌های مختلف در Git استفاده می‌شوند، اما روش انجام این کار و تأثیرشان روی تاریخچه Commitها متفاوت است.

git merge

دستور "git merge" تغییرات یک شاخه را با شاخه فعلی ترکیب می‌کند. اگر دو شاخه به‌صورت جداگانه Commitهای جدید داشته باشند، معمولاً یک Merge Commit ایجاد می‌شود که تاریخچه هر دو شاخه را به هم متصل می‌کند. در این روش Commitهای قبلی تغییر نمی‌کنند و مسیر توسعه شاخه‌ها حفظ می‌شود.
مثلاً اگر بخواهیم تغییرات شاخه "feature-login" را وارد شاخه اصلی کنیم، از دستورهای زیر استفاده می‌کنیم:

git switch main
git merge feature-login

دستور اول ما را وارد شاخه "main" می‌کند و دستور دوم تغییرات شاخه "feature-login" را با آن ادغام می‌کند.
من از Merge زمانی استفاده می‌کنم که در یک پروژه گروهی بخواهیم تغییرات شاخه‌های مختلف را وارد شاخه اصلی کنیم. دلیل انتخابم این است که تاریخچه Commitهای قبلی حفظ می‌شود و می‌توانیم متوجه شویم تغییرات هر شاخه چگونه به پروژه اضافه شده‌اند.

git rebas

دستور "git rebase" تغییرات یک شاخه را روی مبنای جدید دوباره اعمال می‌کند. به این ترتیب Commitهای آن شاخه روی آخرین تغییرات شاخه مقصد قرار می‌گیرند و تاریخچه معمولاً خطی‌تر و مرتب‌تر می‌شود.

مثلاً اگر در شاخه "feature-login" کار می‌کنیم و می‌خواهیم تغییرات جدید شاخه "main" را مبنای کار خود قرار دهیم، از دستورهای زیر استفاده می‌کنیم:

git switch feature-login
git rebase main

دستور اول وارد شاخه "feature-login" می‌شود و دستور دوم Commitهای مخصوص این شاخه را روی آخرین وضعیت محلی "main" دوباره اعمال می‌کند.

من Rebase را برای شاخه شخصی خودم انتخاب می‌کنم، چون باعث می‌شود تاریخچه خطی‌تر و بررسی Commitها ساده‌تر شود.

البته Rebase می‌تواند شناسه Commitهای بازاعمال‌شده را تغییر دهد؛ به همین دلیل روی شاخه‌های مشترکی که دیگران هم از آن‌ها استفاده می‌کنند، بدون هماهنگی Rebase انجام نمی‌دهم.

تفاوت اصلی

تفاوت اصلی این دو دستور در شکل تاریخچه است. Merge تاریخچه قبلی شاخه‌ها را حفظ می‌کند و در حالت ادغام دو شاخه منشعب، معمولاً یک Merge Commit می‌سازد. البته اگر ادغام به‌صورت Fast-forward انجام شود، ممکن استCommit جدیدی ایجاد نشود.

سؤال دوم: انتخاب بخشی از تغییرات (Hunk)

در Git، منظور از "hunk" یک بخش از تغییرات فایل در خروجی "git diff" است که معمولاً شامل خطوط تغییرکرده و چند خط اطراف آن‌ها می‌شود.

برای مشاهده تغییرات یک فایل می‌توان از دستور زیر استفاده کرد:

"git diff -- index.html"

اگر بخواهیم فقط بعضی از تغییرات فایل را برای Commit بعدی انتخاب کنیم، از دستور زیر استفاده می‌کنیم:

"git add -p -- index.html"

گزینه "-p" تغییرات را به‌صورت تعاملی و بخش‌به‌بخش نشان می‌دهد. برای هر Hunk می‌توانیم با "y" آن را وارد Staging کنیم یا با "n" از انتخاب آن صرف‌نظر کنیم. گزینه "s" برای تقسیم یک Hunk به بخش‌های کوچک‌تر و "q" برای خروج از حالت تعاملی است.

بعد از انتخاب بخش‌های موردنظر، با دستور "git diff --cached" تغییرات آماده Commit را بررسی می‌کنیم و در نهایت با دستور "git commit -m "Update page title"" آن‌ها را ثبت می‌کنیم.

فایده این روش این است که اگر در یک فایل چند تغییر مختلف داشته باشیم، مجبور نیستیم همه آن‌ها را در یک Commit قرار دهیم. در نتیجه هر Commit می‌تواند مربوط به یک تغییر مشخص باشد و تاریخچه پروژه منظم‌تر و بررسی یا بازگرداندن تغییرات آسان‌تر می‌شود.

سؤال سوم: 

دستور "git bisect" چگونه کار می‌کند؟ مراحل پیدا کردن کامیتی را که یک خطا را وارد کرده است، از مشخص کردن یک کامیت سالم و یک کامیت معیوب تا پایان جست‌وجو، توضیح دهید. یک مثال از کاربرد آن بیاورید و توضیح دهید چرا این روش برای یافتن منشأ خطا مفید است.

پاسخ:

دستور "git bisect" برای پیدا کردن کامیتی استفاده می‌شود که باعث ایجاد یک خطا در پروژه شده است. این دستور با روش جست‌وجوی دودویی کار می‌کند؛ یعنی به‌جای بررسی تمام کامیت‌ها به‌ترتیب، هر بار یک کامیت میانی را برای بررسی انتخاب می‌کند تا محدوده جست‌وجو کوچک‌تر شود.

مراحل انجام کار به این صورت است:

1. ابتدا با دستور "git bisect start" جست‌وجو را شروع می‌کنیم.
2. با دستور "git bisect bad" مشخص می‌کنیم که کامیت فعلی دارای خطاست.
3. با دستور "git bisect good a1b2c3d" یک کامیت قدیمی‌تر و سالم را معرفی می‌کنیم. شناسه "a1b2c3d" در این مثال فرضی است.
4. Git یک کامیت میانی را انتخاب می‌کند. آن را آزمایش می‌کنیم و اگر سالم بود "git bisect good" و اگر خطا داشت "git bisect bad" را اجرا می‌کنیم.
5. این مراحل تکرار می‌شوند تا Git اولین کامیت ایجادکننده خطا را مشخص کند.
6. در پایان با دستور "git bisect reset" از حالت جست‌وجو خارج می‌شویم و به وضعیت قبلی برمی‌گردیم.

مثال: فرض کنیم در یک پروژه طراحی سایت، دکمه ورود قبلاً درست کار می‌کرده، اما بعد از چندین کامیت دیگر کار نمی‌کند. با "git bisect" می‌توانیم مشخص کنیم خطا از کدام کامیت شروع شده است.

دلیل مفید بودن: این روش تعداد کامیت‌هایی را که باید بررسی کنیم کاهش می‌دهد و مخصوصاً وقتی تعداد کامیت‌ها زیاد باشد، باعث صرفه‌جویی در زمان و پیدا کردن سریع‌تر منشأ خطا می‌شود.


سؤال چهارم: 

فرض کنید فایل "README.md" در مخزن tracked است و قبلاً کامیت شده است. بخشی از تغییرات جدید آن را وارد ناحیه staging کرده‌اید و سپس، بدون اجرای دوباره دستور افزودن به این ناحیه، همان فایل را مجدداً ویرایش کرده‌اید. همچنین پوشه‌ای به نام "tmp/" دارید که فقط شامل فایل‌های موقت و untracked است.

۱. با چه دستورهایی وضعیت مخزن، تغییرات هنوز واردنشده به ناحیه staging و تغییرات آماده کامیت را بررسی می‌کنید؟ تفاوت دو دسته تغییرات اخیر را توضیح دهید.

۲. اگر در همین وضعیت یک کامیت معمولی و بدون گزینه "-a" ثبت کنید، کدام تغییرات فایل در آن قرار می‌گیرند و کدام تغییرات باقی می‌مانند؟ دلیل پاسخ خود را بیان کنید.

۳. برای جلوگیری از اضافه‌شدن فایل‌های پوشه "tmp/" به کامیت‌های بعدی، چه تنظیمی و در کدام فایل انجام می‌دهید؟ آیا همین تنظیم برای فایلی که قبلاً tracked شده است نیز کافی است؟ توضیح دهید.

پاسخ:

۱. بررسی وضعیت و تغییرات مخزن

برای بررسی وضعیت فایل‌ها از دستور زیر استفاده می‌کنم:

"git status"

برای مشاهده تغییراتی که هنوز وارد Staging نشده‌اند:

"git diff"

و برای مشاهده تغییراتی که آماده Commit هستند:

"git diff --cached"

تفاوت این دو دسته این است که تغییرات Staged برای Commit بعدی انتخاب شده‌اند، ولی تغییرات Unstaged هنوز وارد ناحیه Staging نشده‌اند.

۲. ثبت Commit در این وضعیت

اگر دستور زیر را اجرا کنیم:

"git commit -m "Update README""

فقط تغییراتی از "README.md" که قبلاً وارد Staging شده‌اند در Commit ثبت می‌شوند. ویرایش‌های جدیدتر که دوباره Stage نشده‌اند در Working Tree باقی می‌مانند.

دلیل این موضوع این است که Commit معمولی، بدون گزینه "-a"، محتوای آماده‌شده در Staging را ثبت می‌کند. فایل‌های Untracked پوشه "tmp/" نیز چون Stage نشده‌اند وارد این Commit نمی‌شوند.

۳. جلوگیری از اضافه شدن فایل‌های موقت

برای این کار در فایل ".gitignore" مخزن، عبارت زیر را قرار می‌دهم:

"tmp/"

با این تنظیم، فایل‌های Untracked داخل پوشه "tmp/" به‌صورت معمول توسط Git نادیده گرفته می‌شوند و به Commitهای بعدی اضافه نمی‌شوند.

اما اگر فایلی از قبل Tracked شده باشد، اضافه کردن آن به ".gitignore" کافی نیست. برای خارج کردن آن از پیگیری Git، بدون حذف فایل از سیستم، می‌توان از دستور زیر استفاده کرد:

"git rm --cached -- filename"

سپس باید این تغییر را Commit کرد. در این دستور "filename" نام فایل موردنظر است.


سؤال پنجم: 

شما و هم‌تیمی‌تان از یک کامیت مشترک شروع کرده‌اید. شما در branch "feature-description" و هم‌تیمی‌تان در branch "main"، یک خط از فایل "README.md" را به دو متن متفاوت تغییر داده و کامیت کرده‌اید. همه تغییرات ثبت شده‌اند و working tree در وضعیت clean است؛ یعنی تغییر ثبت‌نشده‌ای ندارید. هنگام merge کردن branch شما در "main"، Git برای این خط conflict گزارش می‌کند.

۱. چرا این conflict رخ داده است؟ آیا هر تغییری که دو نفر در یک فایل ایجاد کنند الزاماً باعث conflict می‌شود؟

۲. چگونه فایل‌های دارای conflict و دو نسخه متن را شناسایی می‌کنید؟ نقش conflict markers در فایل را توضیح دهید.

۳. فرض کنید اطلاعات هر دو تغییر باید حفظ شود. از زمان مشاهده conflict تا تکمیل merge چه مراحلی را طی می‌کنید و چه دستورهایی به کار می‌برید؟ چگونه مطمئن می‌شوید که conflict markers در متن نهایی باقی نمانده‌اند؟

۴. اگر هنگام بررسی متوجه شوید که فعلاً نباید این merge انجام شود، با چه دستوری عملیات merge در حال انجام را لغو می‌کنید؟

پاسخ:

۱. دلیل ایجاد Conflict

این مشکل به این دلیل ایجاد شده که دو نفر یک خط مشترک از فایل "README.md" را در دو شاخه به شکل متفاوت تغییر داده‌اند و Git نمی‌تواند خودش تصمیم بگیرد کدام متن را نگه دارد.

البته هر تغییری در یک فایل باعث Conflict نمی‌شود. اگر تغییرات در قسمت‌های جداگانه باشند و با هم تداخل نداشته باشند، Git معمولاً می‌تواند آن‌ها را خودکار ادغام کند.

۲. شناسایی Conflict

برای مشاهده وضعیت مخزن و فایل‌های دارای Conflict از دستور زیر استفاده می‌کنم:

"git status"

همچنین برای نمایش نام فایل‌های دارای Conflict حل‌نشده می‌توان از دستور زیر استفاده کرد:

"git diff --name-only --diff-filter=U"

داخل فایل، Git معمولاً با علامت‌های "<<<<<<< HEAD"، "=======" و ">>>>>>> feature-description" دو نسخه متفاوت متن را مشخص می‌کند.

قسمت اول مربوط به شاخه فعلی یعنی "main" و قسمت دوم مربوط به شاخه "feature-description" است.

۳. مراحل رفع Conflict

ابتدا فایل "README.md" را باز می‌کنم و هر دو نسخه متن را بررسی می‌کنم. چون باید اطلاعات هر دو تغییر حفظ شود، یک متن نهایی می‌نویسم که شامل اطلاعات هر دو باشد و علامت‌های Conflict را حذف می‌کنم.

سپس فایل را ذخیره می‌کنم و دستورهای زیر را اجرا می‌کنم:

"git add README.md"

"git status"

"git diff --cached -- README.md"

"git diff --check"

با بررسی فایل و این دستورها مطمئن می‌شوم متن نهایی درست است، علامت‌های Conflict باقی نمانده‌اند و فایل برای Commit آماده شده است.

در پایان، اگر Conflict حل‌نشده دیگری وجود نداشته باشد، با دستور زیر ادغام را تکمیل می‌کنم:

"git commit -m "Resolve README merge conflict""

۴. لغو عملیات Merge

اگر تصمیم بگیرم فعلاً ادغام انجام نشود، از دستور زیر استفاده می‌کنم:

"git merge --abort
این دستور عملیات Merge در حال انجام را لغو می‌کند و در شرایط این سؤال که قبل از ادغام تغییر ثبت‌نشده‌ای نداشتیم، وضعیت قبل از Merge را برمی‌گرداند.
در مقابل، Rebase با بازاعمال Commitها روی مبنای جدید، معمولاً تاریخچه خطی‌تری ایجاد می‌کند، اما شناسه Commitهای بازاعمال‌شده تغییر می‌کند.
در نتیجه برای ادغام تغییرات در پروژه گروهی معمولاً Merge را مناسب‌تر می‌دانم و برای مرتب کردن تاریخچه شاخه شخصی، Rebase را انتخاب می‌کنم.

سؤال ششم: 

در هر یک از موقعیت‌های مستقل زیر، توضیح دهید چه می‌کنید، چه دستورهایی به کار می‌برید و چه اثری بر working tree، ناحیۀ staging یا تاریخچۀ کامیت‌ها می‌گذارند. فرض کنید هنگام اجرای دستورهای بازگردانی conflict رخ نمی‌دهد.

۱. در فایل tracked به نام "notes.txt" تغییری ایجاد کرده‌اید که دیگر آن را نمی‌خواهید. این تغییر وارد ناحیۀ staging نشده است و نسخۀ موجود در این ناحیه با آخرین کامیت یکسان است. می‌خواهید فقط تغییرات این فایل کنار گذاشته شوند و فایل‌های دیگر دست‌نخورده بمانند.

۲. تغییرات "notes.txt" را اشتباهاً وارد ناحیۀ staging کرده‌اید، اما هنوز کامیت نکرده‌اید. می‌خواهید فایل از این ناحیه خارج شود، ولی ویرایش‌های شما در working tree حفظ شوند.

۳. یک کامیت اشتباه معمولی، نه merge commit، را روی branch مشترک "main"، push کرده‌اید و هم‌تیمی‌ها نیز آن را دریافت کرده‌اند. working tree در وضعیت clean است. می‌خواهید اثر این کامیت را بدون حذف یا بازنویسی تاریخچه بازگردانید. روش مناسب چیست و چرا حذف کامیت از تاریخچه و force push در این موقعیت انتخاب مناسبی نیست؟

پاسخ

۱. حذف تغییرات Stageنشده فایل

برای کنار گذاشتن تغییرات فایل "notes.txt" از دستور زیر استفاده می‌کنم:

"git restore notes.txt"

این دستور فایل را در Working Tree به نسخه موجود در Staging برمی‌گرداند. چون طبق سؤال نسخه Staging با آخرین Commit یکسان است، تغییرات جدید فایل حذف می‌شوند و فایل به آخرین نسخه ثبت‌شده برمی‌گردد.

این دستور فقط روی "notes.txt" اثر می‌گذارد و فایل‌های دیگر را تغییر نمی‌دهد. ناحیه Staging و تاریخچه Commitها هم تغییر نمی‌کنند.

۲. خارج کردن فایل از Staging بدون حذف ویرایش‌ها

از دستور زیر استفاده می‌کنم:

"git restore --staged notes.txt"

این دستور تغییرات فایل را از Staging خارج می‌کند، ولی ویرایش‌های موجود در Working Tree را نگه می‌دارد.

بنابراین می‌توانم بعداً دوباره تغییرات را بررسی و در صورت نیاز با "git add notes.txt" برای Commit آماده کنم. تاریخچه Commitها هم تغییر نمی‌کند.

۳. خنثی کردن Commit اشتباه در شاخه مشترک

در این وضعیت از دستور "git revert" استفاده می‌کنم.

ابتدا با دستور زیر شناسه Commit اشتباه را پیدا می‌کنم:

"git log --oneline"

سپس دستور زیر را اجرا می‌کنم:

"git revert a1b2c3d"

شناسه "a1b2c3d" فرضی است و باید با شناسه Commit اشتباه جایگزین شود.

این دستور اثر Commit اشتباه را با ایجاد یک Commit جدید خنثی می‌کند، بدون اینکه Commit قبلی را از تاریخچه حذف کند. در نتیجه تاریخچه حفظ می‌شود و تغییرات خنثی‌کننده در نسخه پروژه ثبت می‌شوند.

بعد از بررسی نتیجه، با دستور زیر Commit جدید را به مخزن مشترک ارسال می‌کنم:

"git push origin main"

از حذف Commit قبلی و "force push" استفاده نمی‌کنم، چون هم‌تیمی‌ها آن Commit را دریافت کرده‌اند. بازنویسی تاریخچه مشترک می‌تواند باعث ناهماهنگی بین مخزن افراد و ایجاد مشکل هنگام ادامه کار گروهی شود.

نتیجه: برای حذف تغییرات Stageنشده از "git restore"، برای خارج کردن تغییرات از Staging از "git restore --staged" و برای خنثی کردن Commit منتشرشده از "git revert" استفاده می‌کنم.
